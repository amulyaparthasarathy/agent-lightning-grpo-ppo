# Budget-bounded exploratory matched report

This is a separate `exploratory-matched-20-v1` study protocol using the existing
`matched-rollout-mean-v2` numerical backend. It does not relax or replace the
formal ten-job campaign's new-holdout, pilot or admission gates.

No cloud jobs, image builds, qualification, probe, training, merge, Secret changes
or Volume writes were executed while preparing this change. Existing attempts
were inspected read-only first: a01 App `ap-IZ5DyjATiXCKQ24RriasXN` was stopped
with zero tasks; a02 had no submission, owner, index or stop record. Evidence is
in `evidence/phase2-exploratory/{apps,attempts}-before.json`. An additional launch
check leaves any active or unresolved a02 untouched. Old plans/evidence remain
preserved; the old a02 plan is not the new exploratory qualification plan.

## Frozen design

- Report phase `exploratory`: **three paired seeds 2001, 2002, 2003**, each with
  one GRPO and one PPO-MC run: **six jobs, 20 steps each, concurrency two** (two rolling GPU lanes).
- Qualification phase `exploratory-qualification`: seed **9101**, one job per
  algorithm, **two steps**, concurrency two. These are plumbing checks, not
  selected report seeds. Six qualification stages precede 18 report stages.
- Both phases use the exact frozen prepared **64-case development panel**,
  labeled **exploratory-legacy-64** in plans and W&B. The historical data manifest
  retains its old `final_heldout_cases` key for byte identity; that historical
  name is not an untouched-final-test claim.
- Every job starts from the prepared, untrained base, runs a matched-route
  no-update baseline, trains, then independently reloads its final native
  checkpoint for evaluation. The Stanford bootstrap baseline is not repeated.
- Each run saves only its final checkpoint (step 2 or step 20). Actor and critic
  role files form one native PPO checkpoint. No checkpoint or historical artifact
  is deleted. An extra checkpoint causes a policy failure, not pruning.
- Common retention, fragment-invariant reductions, optimizer normalization,
  numerical source locks and actual seed wiring are unchanged. W&B identities,
  paths, source/data hashes and per-stage observability are generated by the same
  matched contract. Group: `agl-explore-20-v1-exploratory`; qualification has its
  own `agl-explore-20-v1-exploratory-qualification` group.
- One source is committed and frozen **before** both plans are generated. The
  completed short qualification must match that exact source and data before
  report launch. There is **no additional standalone 20-step pilot** and **no
  separate ten-GPU admission probe** in this protocol.
- No retries, timeout extensions, automatic reserve release, seed substitutions,
  best-checkpoint selection or outcome-dependent run selection. Both phases use
  attempt 1 in their new namespace. Atomic report-allocation reservations also
  prevent spending the same phase allocation again after an ambiguous launch.

Include every planned seed and all failures in the report, with per-seed baseline
and final development accuracy, paired differences, optimizer/step completion,
wall time, costs, tool/format failures and uncertainty. Never replace a failed run
or discard an unfavorable seed. With three pairs and a repeatedly used development
panel, results are exploratory; no confirmatory generalization claim follows.
Independent trace review and the existing independent numeric grader remain useful
checks, but do not turn the panel into a new holdout.

## Time and resource limits

| Phase | Baseline | Training | Independent reload | Startup watchdog | Supervisor |
|---|---:|---:|---:|---:|---:|
| Short qualification | 30 min | 15 min / 2 steps | 30 min | 5 min within each stage | 85 min |
| Six-job report | 30 min | 90 min / 20 steps | 30 min | 5 min within each stage | 460 min |

Stage age starts at submission. Queueing, startup, hashing, model loading,
checkpoint saving and receipt work count inside the limit; the subprocess gets
only the remaining time, with shutdown/receipt margins deducted. The supervisor
uses the same stage-specific deadlines, checks cumulative worker time/cost, and
cancels only owned calls. No deadline is increased to finish a slow run.

Both phases request the existing **H100!, 16 physical CPUs and 196608 MiB RAM**
per worker. Exploratory workers additionally cap CPU and RAM at those values;
OOM or throttling is a failure to report, not permission to enlarge resources.
Supervisors request/cap 1 CPU and 2048 MiB. Existing CUDA/VERL build layers,
Secret and prepared Volume are reused; no forced CUDA build is requested.
Actual scheduling may deliver fewer simultaneous GPUs. The launcher never
substitutes a separate capacity probe or unrequested sequential batch.

## Funding: $300 maximum, reserve unavailable

| Allocation | Maximum | Treatment |
|---|---:|---|
| Qualification | $50 | Includes its workers and supervisor; one attempt |
| Study workers | $150 | 6 × (0.5 + 1.5 + 0.5) hours × $10/hour |
| Other overhead | $25 | Study supervisor, bounded collection, storage and incidental overhead |
| Contingency | $75 | Locked; requires separate approval and a reviewed plan before use |
| Total | **$300** | Initial operational envelope is **$225**, not $300 |

The plan's `budget_usd` is $50 for qualification and $175 for the report
($150 workers + $25 overhead); the report has an additional independent $150
worker-cost gate. The supervisor's reporting rate is bounded at $1/hour, rather
than charging a CPU supervisor at the H100 worker ceiling. The $75 reserve is
present as an allocation but `reserve_released_usd` is fixed at zero. No unused
qualification funds or reserve are automatically transferred to another run.

Conservative planned compute:

- Qualification: 2 × 75 min = **2.5 worker-hours / $25** plus up to
  **$1.4167** supervisor = **$26.4167**, within its $50 allocation.
- Study: **15 worker-hours / $150** plus up to **$7.6667** supervisor.
- One final checkpoint per job: approximately **442.8 GiB** including both
  qualification jobs and all six report jobs, using previously observed
  37.39 GiB GRPO / 73.31 GiB PPO checkpoint sizes. Budget **600 GiB** of
  incremental Volume storage for new outputs; this is a planning allowance, not
  measured free capacity. The existing worker startup check requires **100 GiB**
  of actual local scratch headroom.
- Budget storage over **seven days** at a conservative full 600 GiB occupancy:
  **$12.60**. Budget at most **10 GiB collected per phase**, 20 GiB total,
  at **$0.80**. Collection excludes native weights and fails closed at its byte
  ceiling; use one final collection per phase. Repeated downloads are not budgeted.
- Study supervisor + modeled storage/collection = **$21.0667** of the $25
  overhead allocation, leaving **$3.9333** for incidental overhead. Combined
  modeled compute/storage/collection upper estimate is **$197.4834**; the full
  $225 operational allocation remains the bound, with $75 held separately.

For context, the [Modal pricing page](https://modal.com/pricing) inspected during
preparation listed H100 $0.001097/s, CPU $0.0000131/core/s, memory
$0.00000222/GiB/s, Volume $0.09/GiB/month and egress $0.04/GiB.
At requested resources this is approximately **$6.238224 per worker-hour**,
below the $10 assumption. No free credits or free storage/egress allowance are
counted. Assume standard preemptible Functions, no region premium, existing
workspace subscription and cached CUDA layers. Recheck rates and workspace usage
before authorization. These are application bounds and conservative estimates,
not a provider billing hard lock; provider termination/billing lag can occur.

Persistent storage can continue accruing charges after seven days. No automatic
deletion is authorized. Before launching, accept this finite cost horizon and a
retention decision by day seven; continued storage, extra collection or other
unbudgeted work needs review within the $300 maximum. Reserve cannot fund it
without separate approval. A missing verified price/capacity/storage assumption
is a launch blocker, not a reason to spend contingency silently.

## Frozen plans and bounded admission

Both source-bound plans must be regenerated after the final clean commit:

```bash
uv run --locked python scripts/phase2_study.py plan \
  --phase exploratory-qualification --study-id agl-explore-20-v1 --attempt 1 \
  --data-manifest evidence/phase2-prepared-data-manifest.json \
  --plan .local/exploratory/qualification-plan.json
uv run --locked python scripts/phase2_study.py plan \
  --phase exploratory --study-id agl-explore-20-v1 --attempt 1 \
  --data-manifest evidence/phase2-prepared-data-manifest.json \
  --plan .local/exploratory/study-plan.json
```

The explicit `launch --bounded-admission` option is valid only for these two
exploratory phases. It requires the existing exact `--authorize` plan digest,
clean matching source, unchanged data/protocol/resources/funding, plus
`--owner-gross-headroom-usd` and `--reviewed-usage-limit-usd 600`. It cannot be
combined with `--capacity`, or used for formal qualification/pilot/campaign.
Without this option, the existing capacity-evidence validator still applies.

Bounded admission verifies the authenticated workspace is `amulyasp`, and the
existing prepared Volume is V1 with ID `vo-SfQGusN1IqkAw5A3o0fiE7`. Read-only
inventory and billing are checked before submission. When current billing is
available, usable gross headroom is the smaller of the owner's confirmation and
$600 minus metered usage. Billing API unavailability is recorded and the explicit
owner confirmation remains authoritative. A known wrong workspace/Volume or
insufficient billing headroom rejects launch. No custom spend limit, credit
balance or provider-enforced per-study budget is invented; credits add no budget.

GPU/container quota numbers, aggregate CPU/RAM quota applicability and current
CUDA/VERL cache residency remain **unverified**, explicitly recorded in an
`*.admission.json` receipt. Actual Modal admission and image-cache resolution
determine availability. Published plan limits and prior successful Stanford H100
execution are supporting context only. The existing CUDA layers are reused
without forcing a rebuild; no model download or bootstrap baseline is added.
There are three potential V1 writers (two workers and one supervisor), with
disjoint worker paths and a sole aggregate-index writer. No Volume migration,
deletions, or placeholder free-space attestations are used. Workers still check
100 GiB local scratch. Formal campaign gates are unchanged.

Reservations prevent duplicate attempts and repeated allocations. A provider
rejection or ambiguous launch preserves reservation and local failure evidence;
there is no resubmission, seed replacement, deadline extension or reserve access.
Stage and supervisor limits, cost counters and completion evidence requirements
remain enforced. The report supervisor is bounded to three two-job waves:
3 × (30 + 90 + 30) + 10 = 460 minutes. Qualification stays at 85 minutes.
The combined remote envelope is **545 minutes / 9h05m**, leaving time within the
runner's 12-hour limit for submission/cache resolution and collection. This is a
bound, not a guarantee that a provider or training failure will recover.

## Overnight runner

The supplied runner lives at ignored `.local/exploratory/phase2_overnight.py`;
its reviewed bytes and offline-test receipt are recorded separately. Dry run:

```bash
uv run --locked python .local/exploratory/phase2_overnight.py --repo .
```

Only the owner may invoke its paid mode with **both** explicit allocations:
`--execute --approve-qualification-usd 50 --approve-study-usd 175` and
`MODAL_PROFILE=amulyasp`. The owner confirmation of gross headroom defaults to
the supplied $598.46 and can be refreshed with `--owner-gross-headroom-usd`;
the CLI rechecks live billing before each submission when available.

The runner submits qualification once, requires all six completed stages and a
successful actual supervisor result, and collects once. Only verified same-source
qualification permits one report submission, processing six jobs/18 stages on two
GPU lanes. It checks collected receipts, W&B identities, native checkpoint
identities and independent reload hashes, then writes
`.local/exploratory/study-collected/overnight-summary.json` from actual evidence.
Native weight files remain on the Volume. Hosted W&B and provider billing still
need independent reconciliation; the legacy panel remains exploratory.

A persistent local deadline, process lock, submission intents, server reservations
and collection intents prevent deadline resets, duplicate runners and blind
resubmissions/downloads. Verified existing submissions may be attached after a
manual restart; ambiguous intents require investigation, never automatic retry.
On failure or deadline the runner requests `stop-owned` for the current phase,
records the failure and does not launch the next phase. Cancellation requested is
not proof that termination finished; inspect the exact owned calls if uncertain.
No reservation is cleared and no historical artifact is overwritten.

**Keep Windows/WSL awake.** The local orchestrator must run to submit the report
after qualification. If it sleeps/disconnects, the currently detached Modal phase
continues under its remote limits; the next phase cannot auto-launch until the
runner resumes, and only within the original 12-hour deadline. `nohup` protects
against terminal closure, not laptop sleep. This is not cloud-only chaining.

One-command operations, using `qualification-plan.json` or `study-plan.json`:

```bash
MODAL_PROFILE=amulyasp uv run --locked python scripts/phase2_study.py status --plan .local/exploratory/study-plan.json
MODAL_PROFILE=amulyasp uv run --locked python scripts/phase2_study.py collect --plan .local/exploratory/study-plan.json --out .local/exploratory/study-collected
MODAL_PROFILE=amulyasp uv run --locked python scripts/phase2_study.py stop-owned --plan .local/exploratory/study-plan.json
```

Do not run a second collection alongside the runner. Inspect overnight logs and
summary the next day; report any missing/failed stages without favorable selection.
